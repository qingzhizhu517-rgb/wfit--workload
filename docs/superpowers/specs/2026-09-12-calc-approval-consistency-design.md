# 核算与审批一致性优化设计

## 背景与目标

当前 M1-M5 核心功能已全部落地，附件1/2、批量核算、两级审批、教师总览和因子追溯均可用。最近审查已修复终态 `status=2` 漂移、导出状态翻译、锁定汇总删除、导出前置条件及若干 UI/验证脚本问题。下一阶段不再扩张业务功能，聚焦“审批期间数字不可漂移、并发情况下终态不可被覆盖、状态定义只有一个来源、批量核算可观测”。

## 方案比较与选择

1. **仅收口常量**：将 Java 中的 0/1/2 全部替换为 `WorkloadSummaryStatus`。成本最低，能避免再次出现 2/3 漂移，但无法解决检查后写入的并发竞态。
2. **状态冻结 + 条件更新（采用）**：待审和已完结均禁止持久化重算；汇总保存使用“预期状态”条件更新并检查影响行数；审批仍用现有原子 SQL。改动集中、无需新增基础设施，可直接覆盖当前风险。
3. **行锁/版本号 + 异步任务**：为汇总、酬金和批量核算引入版本列、任务表与后台执行器。并发语义最强，但涉及 DDL、任务恢复、进度 API 和前端轮询，超过本轮必要范围。

本阶段采用方案 2，并保留方案 3 作为后续性能阶段。

## 架构与改动范围

### 1. 状态契约

`WorkloadSummaryStatus` 是 Java 侧唯一状态定义：`DRAFT=0`、`PENDING_AUDIT=1`、`FINISHED=2`。审批服务、汇总控制器、明细/汇总/酬金核算服务和仪表盘统计统一引用它。MyBatis XML 保持显式参数化状态，不复制业务常量。

### 2. 冻结边界

- `DRAFT`：允许修改明细、重算汇总和酬金。
- `PENDING_AUDIT`：禁止修改明细和持久化重算；允许只读预览，避免查看详情被错误阻断。
- `FINISHED`：禁止修改、删除和任何持久化重算；管理员须先走审计化解锁。

冻结校验应在 service 领域入口，而不是仅依靠 controller 或教师角色判断，确保教务端、子表 CRUD、批量核算和直接 API 调用使用同一约束。

### 3. 并发写入

汇总重算现有流程是先查询状态、计算、再按 `id` 无条件更新。改为专用 Mapper 更新：`WHERE id = ? AND status = DRAFT`，并且不更新 `status`、签字和锁定字段。影响行数不是 1 时抛 409 风格业务异常，提示刷新重试。这样即使审批在计算过程中将状态从 0/1 改为 2，旧计算结果也不能覆盖终态。

酬金重算在写 `biz_pay_record` 前再次验证汇总仍为草稿；后续若需要更强隔离，再为 pay record 增加基于 summary 版本的乐观锁，本阶段不扩表。

### 4. 批量核算

保留现有“每位教师独立事务、失败继续”的语义。返回值增加实际 `recalcItemCount` 汇总，前端不再显示固定 0；待审/完结教师作为明确失败项返回。同步 HTTP 暂保留 5 分钟前端超时，下一阶段再引入任务化进度。

## 错误处理

状态冲突统一使用可识别的 `ServiceException`，文案包含当前状态和“刷新后重试/先解锁”。批量入口记录教师标识与原因，不吞掉状态冲突。只读预览不持久化，因此允许读取待审和终态数据，但必须明确结果是当前规则下的预览，不覆盖已签数据。

## 测试策略

1. 单元测试覆盖草稿允许、待审拒绝、终态拒绝三态矩阵。
2. Mapper/服务测试模拟“读取草稿后并发审批”的影响行数为 0，断言抛冲突且不写回状态。
3. 子表 CRUD 通过共享 `assertEditable` 覆盖待审冻结。
4. 批量核算覆盖明细计数聚合和单人状态冲突不影响其他教师。
5. 完整执行 `mvn test -pl workload-system -am`、变更前端定向 ESLint、`npm run build:prod` 与 `git diff --check`。

## 实施顺序

1. 收口状态常量和契约测试。
2. 将待审纳入明细/持久化核算冻结边界。
3. 新增汇总条件更新，消除审批/重算竞态。
4. 加固酬金写入前状态复核。
5. 补齐批量核算明细计数与前端提示。
6. 全量验证、复审并按独立逻辑提交。
