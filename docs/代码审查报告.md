### 3.1 审批流与数据一致性（P1 组）

<details>
<summary><b>P1-01｜Major｜审批状态机全部写在 Controller，Service 仅裸 CRUD</b></summary>

## 四、设计改进建议

### ① 审批流重构方案

目标：把审批从"Controller 里的手工状态改写"升级为"可审计、抗并发、有领域载体的状态机"。

1. **状态机下沉 Service**（承接 P1-01）：新增审批领域服务（如 `BizAuditService`），以显式迁移表定义合法迁移（动作 × 当前状态 → 目标状态 × 所需角色），submit/approve/reject/sign/unlock/batchSubmit 全部收口于此；Controller 仅保留参数绑定与 `@PreAuthorize`。
2. **原子条件更新**（承接 P1-02）：所有状态变更改为 `update ... set status=#{to}, ... where id=#{id} and status=#{from}`，以影响行数判定成败，失败返回"状态已变更，请刷新"；如需更强保护可叠加 `version` 乐观锁。
3. **事务化**（承接 P1-02/P1-03）：状态变更 + `biz_audit_log` 写入 + 驳回原因落库在同一 `@Transactional` 方法内，保证"状态、痕迹、原因"三者一致。
4. **新增审批日志表 `biz_audit_log`**（承接 P1-03/P1-05）：字段建议 `id, summary_id, action, from_status, to_status, operator_id, operator_name, reason, extra(json), create_time`；reject 原因写此表而非覆盖 remark，天然保留多次驳回历史。
5. **教师确认环节补全**（承接 P1-04/P3-02）：后端开放教师本人确认接口，写入 `teacher_sign`/`teacher_sign_time`（用显式 update 规避 P1-11 同类 null 陷阱）；前端在本人汇总详情提供确认入口；确认作为汇总进入锁定前的必经状态，纳入状态机迁移表。
6. **角色-环节断言**（承接 P2-03）：Service 层对每个动作断言"当前用户角色 ∈ 该环节允许角色"，与 SQL 授权修正双保险。

### ② 事务边界调整

1. **recalcAll 编排事务化**（承接 P1-07/P1-12）：Service 层新增带 `@Transactional` 的编排方法，明细重算→汇总重算→酬金重算单事务提交；入口先校验 userId 存在性，杜绝零值脏数据。
2. **batchSubmit 回执化**（承接 P1-09）：保持逐条处理（避免一条失败整批回滚），但返回结构化回执 `{successCount, failCount, failures:[{id, name, reason}]}`；失败原因区分"状态不符/异常"，前端可展示失败明细；异常不得仅 `log.warn`。
3. **insert-or-update 竞态处理**（承接 P1-10）：汇总/酬金写入改 `ON DUPLICATE KEY UPDATE`（或捕获唯一键冲突后转更新），消除 check-then-act 窗口；配合 P2-07 修复，避免裸 DuplicateKey 信息外泄。

### ③ 权限模型修正

1. **授权纠正**（承接 P2-03/P3-03，前后端双路实测同根因）：`system:audit:approve`(20206) 由院领导 role5 移给教务助理 role3；`system:audit:reject`(20207) 授予 role3；`system:audit:submit`(20205) 增授教师角色（修复教师提交按钮不渲染）；sign→role5、unlock→admin 维持。
2. **teacher 数据范围统一收口**（承接 P2-01/02/04/06/P2-10）：将分散在 6 处的 `"teacher".equals(roleKey)` if 块收敛为统一切面或工具方法（如 `DataScopeUtil.resolveTargetUserId(paramUserId)`：teacher 强制返回本人，管理角色返回入参），导出、预览、生成 G11、新增明细、getInfo 全部接入；从机制上根除 IDOR，而非逐接口打补丁。
3. **端点设防**（承接 P2-05）：Dashboard 三端点补 `@PreAuthorize`；全局检索确认无其他漏注解的 biz 端点。
4. **异常脱敏**（承接 P2-07）：兜底异常处理统一文案，杜绝权限/结构探测信息源。

### ④ 前端改进（按前端审查实测结论）

1. **补教师确认/异议/申诉交互**（承接 P3-02，联动设计改进①第 5 点）：myWorkload/workloadItem/workloadSummary/TeacherDashboard 按记录状态渲染"确认/提异议/申诉"入口，对接后端新接口，形成申报→核对→确认→异议→申诉的完整闭环，终结"有字段无流程"断链。
