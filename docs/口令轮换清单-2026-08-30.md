# 口令轮换操作清单（方案 C）

> 本清单需**你本人执行**：涉及数据库账号权限变更与密钥生成，不由 AI 代跑。
> 执行完请把本文件里填过真实口令的副本删除，或确保它不被提交（仓库根 `.env` 已 gitignore）。
>
> **为什么必须做这一步**：`refactor(security)` 那次提交只是让今后的代码不再带明文，
> 已经泄露过的口令仍然有效 —— 只有换掉它们，泄露才真正失去意义。

---

## 1. MySQL：建专用账号，停用 root 远程直连

当前后端用 `root` 连业务库，权限过大且口令已泄露。改为仅授权 `wflg_workload` 的专用账号。

以 root 登录 MySQL 后执行（把 `<强口令>` 换成实际值，建议 16 位以上随机串）：

```sql
-- 1) 建账号（MySQL 8 默认 caching_sha2_password，无需显式指定）
CREATE USER 'wfit'@'localhost' IDENTIFIED BY '<强口令>';

-- 2) 只授业务库权限，不给 GRANT OPTION、不给其他库
GRANT SELECT, INSERT, UPDATE, DELETE, EXECUTE ON wflg_workload.* TO 'wfit'@'localhost';

-- 3) Quartz 定时任务需要建/删临时表；若启用了 quartz 模块则追加
GRANT CREATE, DROP, INDEX, ALTER, REFERENCES ON wflg_workload.* TO 'wfit'@'localhost';

FLUSH PRIVILEGES;

-- 4) 核对
SHOW GRANTS FOR 'wfit'@'localhost';
```

> 为什么用 `'wfit'@'localhost'` 而不是 `'wfit'@'%'`：后端与数据库同机，
> 限定 localhost 可挡掉一切远程连接尝试。若将来后端与库分离，再按实际网段放开。

**同时给 root 换个新口令**（它已泄露）：

```sql
ALTER USER 'root'@'localhost' IDENTIFIED BY '<root新口令>';
FLUSH PRIVILEGES;
```

⚠️ 改完 root 口令后，本机 `.mcp.json` 里的 `MYSQL_PASSWORD` 也要同步更新，
否则 MySQL MCP 工具连不上。建议顺手把 `.mcp.json` 也改成用 `wfit` 账号。

## 2. JWT 签名密钥

这是本次风险最高的一项：密钥泄露 = 任何人可伪造包含 `admin` 身份的令牌，
不需要密码即可以任意身份调用所有接口。

生成新值（任一）：

```bash
# Git Bash / WSL
openssl rand -base64 48

# PowerShell（无 openssl 时）
[Convert]::ToBase64String((1..48 | ForEach-Object { Get-Random -Max 256 }))
```

把结果填入 `.env` 的 `WFIT_TOKEN_SECRET`。

⚠️ **副作用**：更换后所有已发放令牌立即失效，当前登录的用户全部被踢下线，
需重新登录。开发期无影响；若已有人在用，挑个低峰时段做。

## 3. Druid 监控台

原 `ruoyi` / `123456` 是 RuoYi 框架默认值，属于公开信息，任何人知道你用了
RuoYi 就会去试 `/druid/`。该页可查看运行中的 SQL、连接池状态与部分会话信息。

- 开发环境：`.env` 里设 `WFIT_DRUID_USER` / `WFIT_DRUID_PASSWORD` 为自定义值。
- **对外部署：直接关掉**，改 `application-druid.yml`：

```yaml
statViewServlet:
    enabled: false
```

或保留但限内网访问：

```yaml
statViewServlet:
    enabled: true
    allow: 127.0.0.1,192.168.0.0/16
```

## 4. 应用内账号口令

### 4.1 RuoYi 内置与四个测试账号

`admin/admin123` 与 `admin_test`/`jiaowu_test`/`teacher_test`/`leader_test`（均 `123456`）
来自 `06_test_accounts.sql`，是公开在仓库里的。仅限本地开发。

对外部署前，二选一：

```sql
-- A) 删除测试账号（保留 admin，另行改密）
DELETE FROM sys_user_role WHERE user_id IN (1001,1002,1003,1004);
DELETE FROM sys_user WHERE user_id IN (1001,1002,1003,1004);

-- B) 停用（保留数据关联，避免留下孤儿记录）
UPDATE sys_user SET status='1' WHERE user_id IN (1001,1002,1003,1004);
```

> 若这些账号名下已有工作量数据，选 B 更安全 —— biz 表无外键，
> 删用户会留下孤儿明细（同 `BizTeacherProfileServiceImpl.assertNoRelatedData` 的考虑）。

`admin` 改密：登录后走「个人中心 → 修改密码」，让框架自己加密，
不要直接 UPDATE `sys_user.password`（需匹配 BCrypt 格式）。

### 4.2 教师账号初始弱口令 —— 强制改密已实现

导入新建的教师账号统一发 `WFIT_DEFAULT_PASSWORD`（默认 `123456`）。
口令本身 BCrypt 加密入库，风险不在存储而在"人人皆知初始值"。

**已实现服务端强制改密**（原 CLAUDE.md 待办 #8，现已关闭）：

- `ForcePasswordChangeInterceptor`：`sys_user.pwd_update_date IS NULL`（从未改密）时，
  除白名单外一切请求返回 **602**，前端据此把用户按在改密页，改完才放行。
- 受系统参数 `sys.account.initPasswordModify` 控制（当前值 `1` = 开启）。
  临时关闭：`UPDATE sys_config SET config_value='0' WHERE config_key='sys.account.initPasswordModify';`
- 管理员在「用户管理 → 重置密码」重置后，`pwd_update_date` 被置 NULL，
  用户下次登录仍需自行改密 —— 管理员知晓的口令不算"用户已改过密码"。

因此**教师首次登录必须改密**，不再需要靠 `WFIT_DEFAULT_PASSWORD` 设复杂值来防护
（但设一个不好猜的值仍有意义：防止他人在教师本人首次登录前抢先登录）。

**存量账号处理**：本机当前有 39 个账号 `pwd_update_date` 为 NULL（多为导入的教师），
它们下次登录都会被要求改密 —— 这是预期行为。若想豁免某个账号：

```sql
UPDATE sys_user SET pwd_update_date = NOW() WHERE user_name = '<工号>';
```

## 5. 执行后的验证

```powershell
# 1) 环境变量已注入（IDEA 或 PowerShell）
$env:WFIT_DB_USER='wfit'
$env:WFIT_DB_PASSWORD='<强口令>'
$env:WFIT_DRUID_PASSWORD='<druid口令>'
$env:WFIT_TOKEN_SECRET='<新密钥>'

# 2) 后端能正常启动（起不来先看是不是漏了某个变量）
cd rear
mvn spring-boot:run -pl workload-admin
```

逐项确认：

- [ ] 后端启动无报错，日志中 Druid 连接池初始化成功
- [ ] 故意清空 `WFIT_DB_PASSWORD` 再启动 → **应当启动失败**（验证无默认值生效）
- [ ] 前端能登录（旧 token 已失效，需重新登录）
- [ ] 教学任务导入、汇总重算等读写功能正常（验证 `wfit` 账号权限够用；
      若报权限错误，按报错补 `GRANT`）
- [ ] `/druid/` 用新账密可登入，旧 `ruoyi/123456` 已失效
- [ ] **强制改密链路**：用一个 `pwd_update_date` 为 NULL 的账号（如导入的教师工号
      `T20270005`/初始密码）登录 → 应被弹窗按在个人中心改密页，手动改地址栏跳其他
      菜单也会被弹回；改密成功后自动回首页且功能正常
- [ ] **管理员重置后仍强制**：用 admin 在「用户管理 → 重置密码」重置某教师，
      该教师再登录 → 应仍被要求改密
- [ ] `.mcp.json` 已同步新口令（否则 MySQL MCP 工具不可用）

## 附：为什么不做历史清理（方案 B）

已与你确认暂不执行。要点备忘：

- 改写历史会让 68 个 commit 的 SHA 全变，需 `push --force`，
  所有协作者必须重新 clone（不能 pull）。
- GitHub 仍会保留旧 commit 对象，知道 SHA 即可访问，
  直到开工单请 GitHub Support 做 GC。
- `123456` 这个串在测试账号 SQL、种子数据、文档里到处都是，
  无差别替换会破坏这些文件的可用性。
- 口令轮换后，历史里的旧值已失去价值 —— 清理的收益主要是"看起来干净"。

若将来需要（交付、开源、评审），再按 `git filter-repo --replace-text` 处理，
建议只替换 JWT secret 这一个真正的密钥。
