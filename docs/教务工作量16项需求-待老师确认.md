# 教务工作量 16 项需求——待老师确认的业务口径

> **用途**：本文只请老师确认会影响教学工作量、绩效酬金、审批责任或历史结果的业务口径。页面操作、程序校验、导入报错、缓存更新等技术问题由项目组自行处理，不转交老师判断。
>
> **回复方式**：请在每题末尾勾选一个选项；如选择“其他”，请写明规则及生效学期。为不影响项目推进，本文每题均列出“未回复时默认值”。默认值仅用于继续设计和测试，上线真实数据前仍建议书面确认。
>
> **口径基线**：现行系统按“教师/课程/岗位源数据 → 工作量明细 → 学期汇总 → 酬金 → 审批完结”处理；汇总流程为“填报中 → 教务处待审 → 已完结”。已完结数据当前只能由管理员解锁后返回填报中，原签字会清除并重走审核。

## 问题 1：需求中的第三个数量字段是否确定为“周数”

**背景脉络**
当前教学任务模板把“计划学时、天数、周数”合在一个格子里。16 项需求希望将它们拆开，避免不同课程类别之间混填。现行公式中：G1/G2 使用计划学时，G3 使用天数，G4 使用学分，G5 使用指导人数，G6 使用周数。

**现状与依据**
当前模板表头是“计划学时/天数/周数”，程序对 G6 明确把该值作为周数 `W`，公式为“周数 × 不超过 20 的指导人数 × 0.4”。实施方案中提到需求原文的第三项含义可能不够清楚，因此不能仅凭字段顺序推断。

**为何产生疑问**
如果第三项实际是另一类“学时”，而系统按周数理解，G6 会发生单位错误；反之，如果本应为周数却再次设计成学时，也会导致重复或漏填。

**我们默认采用的合理方案**
将三个数量字段明确命名为“计划学时、天数、周数”；其中“周数”只用于 G6。G4 另填“课程设计学分”，G5 只填指导人数，不再要求填写无意义的占位数。

**不同选择的影响**
- 选“周数”：与当前 G6 公式及既有数据含义一致；旧 G6 数据可按类别迁移为周数。
- 选“另一种学时”：需重新定义适用类别和换算公式；旧 G6 结果不能直接沿用，必须重新对账。
- 选“周数与学时都要”：模板、校验和公式均需增加字段，并需说明二者谁参与计算。

**请老师确认**
- [ ] A. 第三个数量字段就是“周数”，仅供 G6 使用（**建议选项**）
- [ ] B. 第三个数量字段是另一种“学时”，请写明名称、适用类别和公式：________
- [ ] C. 两者都需要，请写明各自适用范围：________

**未回复时默认值**：采用 A。

## 问题 2：花名册“岗位”到系统“人员性质”的映射

**背景脉络**
人员性质不是普通展示字段。现行系统只有“专任”教师计发课时绩效；外聘、校企、银龄、青州外聘等不计课时绩效。花名册中的“岗位”则出现“教师、行政、教师兼行政、银铃教师”等写法，两者不是同一概念。

**现状与依据**
系统允许的人员性质为“专任、外聘、校企、银龄、青州外聘”。现有花名册分析显示，“教师”占多数，另有行政、教师兼行政和银铃教师。当前导入若人员性质留空会默认为“专任”，这对“行政、教师兼行政”可能造成误发绩效。

**为何产生疑问**
“教师兼行政”可能仍属于专任教师，也可能按行政人员口径管理；“行政”人员承担课程时是否领取课时绩效也需制度确认。“银铃教师”与系统字典中的“银龄”是否为同一类也需要确认。

**我们默认采用的合理方案**
“教师→专任”，“银铃教师→银龄”；“行政、教师兼行政”进入待确认清单，不自动赋为专任，也不据此直接发放课时绩效。岗位任职与人员性质分开保存，不能用“职务”反推人员性质。

**不同选择的影响**
- 映射为“专任”：该人员超过额定工作量后可能产生课时绩效。
- 映射为非专任：教学工作量仍可统计，但课时绩效为 0；岗位工作量可另按 G11 计算。
- 暂不映射：可先建立账号和基础档案，但在定性前不应完成酬金结算。
- 改变存量映射：重新核算会改变历史绩效，已完结学期还需走更正流程。

**请老师确认**
- [ ] A. 教师→专任；银铃教师→银龄；行政→________；教师兼行政→________（**建议按类别明确填写**）
- [ ] B. 行政、教师兼行政均按专任
- [ ] C. 行政、教师兼行政均按非专任（请指定系统类别）：________
- [ ] D. 逐人提供人员性质名单，不按岗位批量映射

**未回复时默认值**：教师→专任，银铃教师→银龄；行政、教师兼行政暂不自动定性、不结算课时绩效。

## 问题 3：花名册重复工号与异常字段怎样认定

**背景脉络**
教师账号以工号为唯一识别依据。同名教师可以是两个人，但同一工号不能直接建立两个账号。花名册中已发现至少一组重复工号，且两行的系、教研室、职务信息不一致；另外存在“无”“讲师待遇”等不属于现有标准职称的写法。

**现状与依据**
结构化工作表共有 116 行、115 个初始唯一工号。重复工号对应两条不同组织/职务信息。系统当前只接受教授、副教授、讲师、助教、未定级等标准职称，无法安全地自行猜测“讲师待遇”究竟是正式职称还是待遇口径。

**为何产生疑问**
自动保留第一行会丢失另一段任职事实；自动保留最后一行会覆盖前一条资料；自动合并又可能把两个不同的人误合成一个账号。异常职称若直接映射，会进一步影响额定量、单位酬金和历史结算。

**我们默认采用的合理方案**
以工号为唯一账号；重复工号和无法确定的职称只进入异常清单，阻断相关行导入，不自动选择、不自动合并。老师确认后，可把同一人的多个部门/职务信息拆为“一个主档案 + 多条任职记录”。

**不同选择的影响**
- 保留其中一行：另一行的部门、教研室或任职信息将被舍弃，除非另补岗位记录。
- 合并为同一人：只有一个登录账号；需指定主部门，其余信息转为兼岗/历史任职。
- 认定为两个人：必须更正其中一个工号，否则系统无法区分。
- 异常职称映射为讲师：将使用讲师标准和费率；映射为未定级则使用另一档标准，可能改变绩效。

**请老师确认**
- [ ] A. 重复工号是同一人：主归属系为________，其他信息作为兼岗/历史任职保留
- [ ] B. 重复工号是两个人：请提供更正后的两个工号
- [ ] C. 只保留指定一行：保留依据为________
- [ ] D. 所有重复和异常记录逐条返回老师确认后再导入（**建议选项**）

并请确认异常职称：
- “讲师待遇”映射为：[ ] 讲师  [ ] 未定级  [ ] 仅保留备注、不参与酬金  [ ] 其他________
- “无”映射为：[ ] 未定级  [ ] 仅保留备注、不参与酬金  [ ] 其他________

**未回复时默认值**：采用 D；异常行不进入正式核算，也不输出原始敏感字段。

## 问题 4：测试数据清理范围

**背景脉络**
正式花名册导入前，需要避免测试教师、测试课程、测试岗位和测试核算结果混入真实报表。但“清空测试数据”若理解为清空整张业务表，可能误删已经录入的真实数据、管理员账号、权限或审批记录。

**现状与依据**
仓库中既有初始化演示数据，也可能有专项测试批次和测试账号；它们会关联教学任务、岗位任职、工作量明细、汇总、酬金及审批日志。单删教师账号会留下关联数据，整表删除则影响范围过大。

**为何产生疑问**
需要老师确认哪些数据属于“测试”，以及正式导入前是删除、停用还是保留在独立环境。这个选择关系到历史对账、回滚以及报表是否混入测试人员。

**我们默认采用的合理方案**
正式库仅按经确认的“测试工号白名单”或“测试导入批次”清理其关联业务数据；先生成影响清单并备份，再执行。系统管理员、菜单、角色、规则、费率、真实教师及无法确认归属的数据一律不删。开发/验收库可保留测试数据，但必须与正式库隔离。

**不同选择的影响**
- 白名单删除：最干净，但被删测试结果不再在业务页面可查，需依靠备份恢复。
- 停用保留：可追溯，但报表和人员选择必须默认排除停用记录。
- 整库重建：仅适用于尚无真实数据的环境；所有当前业务数据和审批记录都会消失。
- 整表清空：风险最高，不建议。

**请老师确认**
- [ ] A. 仅删除指定测试工号及其关联数据；名单另附（**建议选项**）
- [ ] B. 仅删除指定测试导入批次及其派生数据
- [ ] C. 测试人员不删除，只停用并从正式报表排除
- [ ] D. 确认当前环境无任何真实数据，可整体重建

请补充：备份保留期限________；允许回滚的时间窗口________。

**未回复时默认值**：采用 A/B 中可明确识别者；无法确认的数据不删除。

## 问题 5：课程源字段变更后，已核算数据如何退回

**背景脉络**
课程级别、课程角色、课程性质、教学评价、专业大类、授课层次、人数、学时/天数/周数等源字段会影响系数或工作量。例如课程级别与课程角色共同影响 Q2；人数和数量字段直接影响多个 G 类公式。

**现状与依据**
当前系统会把计算结果写入工作量明细，汇总进入待审或完结后禁止直接重算。但若教务人员先修改源教学任务而没有同步退回，页面可能同时存在“新源数据”和“旧计算结果”，不利于老师核对。

**为何产生疑问**
业务上需要确定：源字段一变，是自动覆盖结果、自动退回草稿，还是由教师提交调整申请。不同做法决定谁承担确认责任，也决定已签字结果能否保持有效。

**我们默认采用的合理方案**
- 填报中：允许修改，关联明细标记“需重算”，重算后重新核对。
- 教务处待审：源字段变更时自动退回填报中，清除本轮确认/签字，写明退回原因。
- 已完结：禁止直接修改影响结果的源字段，必须走问题 6 的更正流程。
- 纯展示且不影响公式的字段可更正，但仍留修改记录。

**不同选择的影响**
- 自动退回：能保证签字对应最新数据，但增加重新核对工作。
- 只标记不退回：流程较快，却可能在审核中继续看到旧结果，存在误审风险。
- 自动重算不退回：会在审核或签字后静默改数，不建议。
- 一律走申请：控制最严，但普通录入纠错成本较高。

**请老师确认**
- [ ] A. 按上述分状态处理：待审自动退回，完结走更正（**建议选项**）
- [ ] B. 待审只提示“数据已变化”，由教务手工决定是否退回
- [ ] C. 所有影响计算的源字段修改都必须先提交调整申请
- [ ] D. 其他：________

**未回复时默认值**：采用 A，绝不在待审/完结状态静默改数。

## 问题 6：已完结工作量发现错误时的正式更正流程

**背景脉络**
“已完结”表示教务处已审核并锁定，相关结果可能已用于报表或酬金。如果之后发现漏课、人数错误、岗位日期错误或规则适用错误，既要允许纠正，也要保留原结论和责任链。

**现状与依据**
当前系统由管理员执行“解锁”，记录回到填报中；教师和教务签字会被清空，修改、重算后重新提交审核。系统会记录解锁动作，但目前没有单独的“更正单号/更正原因/更正前后差额”业务流程。

**为何产生疑问**
需要明确谁能发起、谁批准、是否允许覆盖原结果，以及若酬金已发放，差额是补发/追回还是留到下一期。该问题不能由程序自行决定。

**我们默认采用的合理方案**
由教师或教务提出更正申请，写明原因和依据；管理员仅在获得教务负责人同意后解锁。系统保留更正前快照，清签后修改、重算并重新走完整审核。若已发放酬金，不改写原支付事实，另形成补发或追回差额记录。

**不同选择的影响**
- 原记录解锁重走：页面最直观，但必须额外保存更正前快照，才能复现原结论。
- 原记录永久保留、另建更正版：审计最清楚，但同一学期会有版本概念，报表需明确“现行版本”。
- 完结后不得更改：流程简单，却无法处理客观错误，只能线下补差。
- 已发酬金直接覆盖：会让账面历史与实际支付不一致，不建议。

**请老师确认**
- [ ] A. 解锁原记录，保留更正前快照并重走审核（**当前可落地的建议选项**）
- [ ] B. 原记录永久封存，另建更正版本
- [ ] C. 已完结只允许线下补差，不修改系统结果

发起人可为：[ ] 教师 [ ] 教务人员 [ ] 学院负责人 [ ] 其他________
解锁批准人：[ ] 教务负责人 [ ] 系统管理员自行判断 [ ] 其他________
已发酬金差额：[ ] 单独补发/追回 [ ] 并入下一期 [ ] 其他________

**未回复时默认值**：采用 A；管理员不能无原因直接更正；已支付金额只记差额，不覆盖原支付事实。

## 问题 7：G11 多岗位叠加和每学期 180 学时封顶

**背景脉络**
同一教师一学期可能同时担任班主任、教研室主任、专业负责人等多个岗位。每个岗位先按任职日期折算为该学期 G11 工作量，再汇总到个人学期结果。

**现状与依据**
当前系统对每条有效岗位任职分别生成一条 G11，并将多条结果相加；G11 学期合计超过 180 时只计 180，并在汇总备注中提示超出。现行计算没有设置“哪个岗位优先计入”的顺序，因为在只看 G11 合计时，先后顺序不改变封顶后的 180。

**为何产生疑问**
如果业务需要在报表中说明“超出的部分属于哪个岗位”，或者不同岗位还关联不同酬金/考核，就必须定义优先顺序；还需确认 180 是只封 G11，还是连 G1-G10 一起封。

**我们默认采用的合理方案**
各岗位按日期分别折算并完整展示；G11 原始合计保留，计入总工作量的 G11 最多 180。180 只限制 G11，不限制 G1-G10；不设置岗位优先级，也不删除超出部分的明细。

**不同选择的影响**
- G11 合计封顶 180：与当前实现一致；超过部分不进入总工作量和绩效，但仍可查明细。
- 每个岗位分别封顶 180：多岗位人员可能计入超过 180，显著提高总工作量和绩效。
- 按岗位优先级占用 180：封顶总数不变，但报表需把部分岗位标为“未计入/部分计入”，历史解释会变化。
- 180 同时封 G1-G11 总量：会大幅改变现行核算结构，与当前规则不同。

**请老师确认**
- [ ] A. 多岗位先分别折算后相加，G11 学期合计封顶 180，不设岗位优先级（**建议选项**）
- [ ] B. G11 合计封顶 180，并按以下岗位顺序优先计入：________
- [ ] C. 每个岗位分别计算、分别封顶或不封顶，请写明：________
- [ ] D. 180 不是 G11 封顶，请写明真实含义：________

超过 180 的部分是否仅展示、不计总量：[ ] 是 [ ] 否，处理方式________

**未回复时默认值**：采用 A；完整保留原始明细和封顶提示。

## 问题 8：教师能否手工申报 G11

**背景脉络**
G11 本质上来自“谁在什么时间担任什么岗位、岗位标准是多少”。现有系统一方面能根据岗位任职自动生成 G11，另一方面教师申报页面也允许选择 G11 并直接填写核定学时，两条路径的凭据强度不同。

**现状与依据**
自动生成的 G11 能追溯到岗位任职、任职日期和折算依据；教师手工申报的 G11 只有项目名称、岗位类型和自填学时，不一定有正式任职记录。当前程序为了不中断核算，会直接采用该自填值，但这并不等于业务上已经同意自由申报。

**为何产生疑问**
若允许自由填数，同一岗位可能既自动生成又手工申报而重复计入，也无法验证任职日期和标准值；若完全禁止，临时岗位或基础资料尚未录入时又可能漏报。

**我们默认采用的合理方案**
教师不能自由填写 G11 学时。正常路径由教务维护/导入岗位任职后自动生成。确有漏录时，教师提交“补录申请”，选择岗位并填写任职区间及证明，教务审核通过后先补岗位任职，再由系统生成 G11，而不是直接采用教师填写的结果。

**不同选择的影响**
- 禁止自由申报：可追溯、避免重复，但需要先完善岗位任职资料。
- 允许基于岗位记录申报：教师可发起，但最终学时仍由系统按日期计算；兼顾效率和审计。
- 允许自由填数并审核：灵活，但审核工作量大，历史结果难以用统一公式复现。
- 保留现状：技术上可算，业务风险是自动与自报重复、无任职依据。

**请老师确认**
- [ ] A. 禁止教师直接填 G11；只能由有效岗位任职自动生成（**最严格选项**）
- [ ] B. 教师可发起岗位补录申请，审核后生成 G11，但不能自由填写最终学时（**建议选项**）
- [ ] C. 教师可直接申报 G11 学时，教务逐条审核；请说明必备证明和防重复规则：________
- [ ] D. 其他：________

**未回复时默认值**：采用 B；在补录流程未完成前，按 A 执行，不允许无任职依据的 G11 进入完结结果。

## 问题 9：规则、岗位标准和酬金费率按哪个时点选择历史版本

**背景脉络**
工作量系数、额定工作量、G11 封顶、岗位标准和职称酬金费率都可能随制度调整而变化。历史学期有时会在新制度生效后才补录或重算。

**现状与依据**
规则表和费率表已有生效起止日期，但当前核算按“执行核算当天”选择有效规则/费率；汇总会保存当次职称和费率数值，却没有完整保存每个规则的版本。于是同一历史学期在不同日期重算，可能得到不同结果。

**为何产生疑问**
必须由业务确定历史归属时点：按学期开始、学期结束、首次核算、审核完结，还是支付日。不同答案都会改变补录、重算及更正结果。

**我们默认采用的合理方案**
工作量规则、岗位标准、额定量和酬金费率统一按“该学期结束日”选择当时有效版本；首次核算时把实际采用的值、生效区间和版本固化到明细/汇总。已完结记录重现时读原快照；只有走正式更正且明确“适用新制度”时才切换版本。

**不同选择的影响**
- 按学期结束日：同一学期口径统一，适合学期结算；制度需明确跨学期生效方式。
- 按学期开始日：学期中调整不影响本学期，稳定性高，但可能晚一个学期执行新政策。
- 按核算/审核日：实现直观，但历史补录会套用新规则，同学期可能不一致。
- 按支付日：适合财务费率，但工作量规则与支付时间绑定，可能不符合教学制度。
- 规则与费率采用不同日期：更精确，但老师需分别明确两个时点。

**请老师确认**
- [ ] A. 规则、岗位标准、费率均按学期结束日（**建议选项**）
- [ ] B. 均按学期开始日
- [ ] C. 工作量规则按________；岗位标准按________；酬金费率按________
- [ ] D. 按首次审核完结时有效版本，之后永不自动变化

新制度能否追溯调整已完结学期：[ ] 不能，除非文件明确要求 [ ] 可以，自生效日起批量更正 [ ] 其他________

**未回复时默认值**：采用 A；新制度默认不追溯已完结学期。

## 问题 10：“职务匹配工作量”是学年值还是学期值

**背景脉络**
花名册含“职务匹配工作量”一列，出现 0、50、90、180 等数值。G11 的岗位标准既有按学年表述的岗位，也有明确按学期表述的例外。如果单位理解错误，结果可能相差一倍。

**现状与依据**
当前系统把普通岗位标准视为学年值，核算某学期时先除以 2，再按任职天数占学期天数的比例折算；“督导 15 学时/学期”不除以 2。

**为何产生疑问**
花名册列名没有注明“每学年”或“每学期”，不能仅凭数值判断。若 90 本来就是学期值却再次除以 2，会少计；若 180 是学年值却不折半，会多计。

**我们默认采用的合理方案**
普通岗位的“职务匹配工作量”按学年值解释；明确写有“每学期”的岗位按学期值。正式导入时同时保存数值和单位，不再仅存一个无单位数字。

**不同选择的影响**
- 学年值：完整任职一个学期通常计标准的一半。
- 学期值：完整任职一个学期计全部标准，普通岗位结果通常是当前口径的 2 倍。
- 按岗位分别定单位：最准确，但需要老师提供岗位目录及单位。

**请老师确认**
- [ ] A. 普通岗位均为学年值；明确标注“每学期”的岗位例外（**建议选项**）
- [ ] B. 花名册该列全部为学期值
- [ ] C. 请按岗位提供“标准值 + 单位（学年/学期）”清单

**未回复时默认值**：采用 A。

## 问题 11：行政、教师兼行政的课时绩效和 G11 关系

**背景脉络**
人员性质决定课时绩效是否计发，岗位任职决定是否产生 G11。行政或教师兼行政人员可能既承担课程，又承担管理岗位，两条规则需要分开确认。

**现状与依据**
现行系统只有人员性质为“专任”才计算课时绩效；G11 则根据有效岗位任职生成，与是否上课无直接关系。制度校验还会对行政岗位采用不同的周学时提示标准，但不能据此反推其酬金资格。

**为何产生疑问**
如果把“教师兼行政”统一映射为专任，可能计发课时绩效；映射为非专任则只统计工作量、不发课时绩效。行政身份本身是否就应生成 G11，也不能由岗位名称猜测。

**我们默认采用的合理方案**
课时绩效以老师确认的人员性质为准；G11 只由正式岗位任职产生，不因“行政/教师兼行政”标签自动给定。未完成定性的人员暂缓酬金结算。

**不同选择的影响**
- 教师兼行政按专任：其教学超额可能产生绩效，管理岗位另计 G11并受 180 封顶。
- 教师兼行政按非专任：教学量保留但课时绩效为 0，仍可有 G11。
- 行政标签自动生成固定 G11：操作简单，但无法区分具体职务、任期和标准，不建议。

**请老师确认**
- 教师兼行政的课时绩效：[ ] 按专任计发 [ ] 不计发 [ ] 逐人认定
- 纯行政人员承担课程时：[ ] 按专任计发 [ ] 不计发 [ ] 逐人认定
- 行政岗位 G11：[ ] 必须有正式岗位任职才生成（**建议**） [ ] 仅凭人员类别自动生成

**未回复时默认值**：课时绩效暂不自动计发；G11 必须有正式岗位任职。

## 问题 12：同一人跨系、兼岗或岗位变化时怎样保存

**背景脉络**
花名册可能出现同一工号对应不同系、教研室或职务。这既可能是当前兼岗，也可能是岗位调整后的历史记录。账号、主部门和岗位任职分别承担不同用途。

**现状与依据**
系统账号只能有一个当前主部门；G11 岗位任职可以有多条，并带起止日期。若把后一行直接覆盖前一行，就无法判断是兼岗还是调岗；若建立两个账号，又会拆散个人工作量和酬金。

**为何产生疑问**
需要老师给出主归属部门的确定原则，以及多条信息是并行兼岗还是前后任职。这会影响学院报表归属、审批范围和 G11 折算。

**我们默认采用的合理方案**
同一工号只建立一个正式账号；指定一个当前主归属系用于人员和学院报表，其他系/教研室/职务作为带日期的兼岗或历史任职保存。无法判断先后关系时阻断该人的正式核算。

**不同选择的影响**
- 一个账号+多任职：个人汇总完整，学院归属需按主部门或课程归属另定。
- 两个账号：可能重复统计人员、工作量和酬金，不建议。
- 仅保留最新一行：历史和兼岗信息丢失，G11 可能少计。

**请老师确认**
- [ ] A. 一个账号、一个主归属系、多条岗位任职（**建议选项**）
- [ ] B. 以每学期主归属系为准，允许主部门随学期变化
- [ ] C. 其他：________

主归属系判定依据：[ ] 人事关系 [ ] 当学期主要授课单位 [ ] 花名册“系”列 [ ] 老师逐人指定
学院报表中的教学工作量归属：[ ] 按教师主部门 [ ] 按课程开课部门 [ ] 其他________

**未回复时默认值**：采用 A；当前主部门按老师最终确认的花名册值，其他信息不丢弃。

## 二、项目组自行处理、不需要老师回答的事项

以下属于技术实现或数据安全措施，将按稳妥原则直接落实，不占用老师确认时间：

1. 导入前提供预览、逐行错误清单和重复校验，不让错误数据静默入库。
2. 不记录、不展示身份证号、住址等非本系统核算必需的敏感明文；联系方式只按授权范围使用。
3. 课程数量字段拆分后，按类别做必填、互斥、正数和单位校验。
4. 导入、修改、生成、核算、审核和解锁都记录操作人、时间及原因。
5. 待审和已完结数据不得被后台重算或源数据修改静默覆盖。
6. 测试数据清理前先备份、生成影响清单，并提供可回滚方案；未获明确授权不做整表删除。
7. 规则或费率修改后及时刷新系统读取结果；技术缓存不得造成页面仍用旧值。
8. 报表继续同时展示计算明细、封顶前数值、实际计入数值和必要说明，方便复核。
