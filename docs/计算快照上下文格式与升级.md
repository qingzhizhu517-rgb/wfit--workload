# 计算快照上下文格式与升级

## 部署顺序

1. 现有库先完成 `rear/sql/23_calculation_consistency.sql`。
2. 部署新后端前执行 `rear/sql/30_snapshot_context.sql`。该补丁只新增可空的 `context_json LONGTEXT`，可重复执行。
3. 来源持久化版本另需 `rear/sql/33_factor_provenance.sql`：仅给明细、其他酬金各加可空证据列，没有历史回填。
4. 启动新应用。旧应用忽略新增列，因此可回滚应用版本并保留该列；不要删除已有新快照上下文。

旧记录保持 NULL，不能用当前课程/规则回填并冒充历史。新代码直接查询 context_json，所以不能先启动新代码后执行补丁。当前仍采用编号 SQL，尚未接入自动迁移。

原本地文件 `28_snapshot_context.sql` 已等字节重命名为 `30_snapshot_context.sql`，避免与远程 `28_import_framework.sql` 冲突。已执行旧文件的环境按列探测确认，不重复改写快照。完整依赖见 `rear/sql/MIGRATIONS.md`。

## 格式与读取

既有列继续保存公式、结果、因子数值、来源、规则标识和哈希。context_json 的 formatVersion=1/2 保存以下基础上下文，format3另增加实际政策及因子/决策证据：

- formulaType、description、reproducible；
- sourceTask：本次构造公式时获得的课程属性；未知字段仍为空，不补造；
- factors：有序的 key、description、status、ruleCode、ruleVersion、sourceRef。

SnapshotContextCodec 统一编解码。数值来自既有 factor_json，按 context 中的因子列表恢复顺序，不依赖 MySQL JSON 对象键顺序。未知格式、损坏 JSON、重复/缺失因子不静默回退当前数据。

format1沿用旧五段payload后追加换行和context原始字符串；format2使用覆盖明细标识/版本及完整证据的结构化canonical SHA-256，兼容JSON键序与DECIMALscale。读取现已校验hash，仍不是防管理员重算hash的签名。v0/v1兼容边界、明确50017错误和实际验证见`验收/T05快照完整性.md`；历史hash不重写。

历史详情只读快照；没有快照时才读当前子表并标记 legacy。旧快照没有保存的课程上下文与说明会明确提示缺失。新快照保留上游已提供的来源引用；旧快照已保存的审批引用继续读取；无快照的物化系数不再按最新批准和值相等追认来源。新批准显式来源持久化属于切片B，其实现与隔离验收进度见 `验收/T05因子与其他酬金来源.md`。

## format4：实际因子选择来源

format4在format3上增加 `persistedFactorSources`。每个来源证明保存类别/因子/值/来源种类、角色、分支内容、完整输入、实际规则内容和引用，并有单独内容摘要；快照外层摘要覆盖完整来源树。`rule_version` 保存政策及因子来源集合的裸64位摘要。format0—3不接受format4扩展字段，旧哈希与解释方式不变。

来源在值产生时保存：导入区分规则、固定分支、显式输入和覆盖值，人工同值改写亦替换旧来源，批准保存完整申请/批准内容，岗位及手工项保存服务端操作者。导入证明保存V1/V2模板版本、冻结转换内容及版本；读取回放原始输入至规范输入，再核对实际计算输入。文本精确比较；数值允许等值scale变化，整数禁止小数截断。

旧物化因子或其他酬金没有来源时保持PARTIAL，不能凭当前值追认政策或批准。其他酬金证据是独立金额格式1，在A—G实际计算分支生成，保存舍入前后金额、输入、完整规则和操作者；插入后绑定实际id、归属、学期、类型和持久化输入，列表与详情均校验。金额表上的证据不是明细format4，亦不是待开发的汇总结算快照。

完整性摘要用于发现损坏和语义不一致，不是防数据库管理员重签的签名机制；实际业务结算与资格门禁仍属于切片C。
