## 1. 总览：两者是什么关系

**不是同一个项目的两个版本，而是同一业务的两个独立实现。**

- 两者依据同一份《潍坊理工学院教师工作量管理办法》（2026 年 1 月修订·征集意见稿）与同一套附件1/附件2。
- 两者都实现了 G1~G6 核算与绩效酬金，关键系数取值**高度一致**（见第 3 节）。
- 但**架构路线、数据模型、功能边界、质量保障完全不同**，且在一处金额级口径上**结论相反**（见第 4 节 D2-1）。
- 两者**不能简单地"合并"**——它们连"系数存在哪里"这个基本问题都给了相反答案。

## 2. 项目 B（副本）全面梳理

### 2.1 定位与三条设计红线（B 的 CLAUDE.md）

> **「这是发钱的系统。」** 每个数字都要能回答「凭什么是这个数」，且任一历史学期的任一数字都能复现出「当时的规则 + 当时的输入 = 这个数」。

1. **核算结果可重现** — 历史学期可复现（靠 `rule_version` 版本化 + 快照内嵌规则版本与因子）
2. **教师不写结果，只写申报** — 系数与结果一律由引擎推导
3. **算式对教师透明** — 每个因子的值与来源直接展示

### 2.2 权威源文件（B 放在 `文档存放/`）

| 文件                            | 作用                         |
| ----------------------------- | -------------------------- |
| `潍坊理工学院教师工作量管理办法(征集意见稿）.pdf`  | 条文依据（2026-01 修订）           |
| `附件1：教师教育教学工作量统计表-新.xlsx`     | 39 列（A~AM）宽稀疏表，**导出目标**    |
| `附件2：教师教育教学工作量绩效酬金统计表-新.xlsx` | 上表每教师一行 + 第 18~19 行起其他酬金明细 |

### 2.3 架构：唯一不可逆依赖边 + 三层

```
workload-domain/   纯 Java 核算引擎；pom 的 enforcer 禁 Spring/MyBatis/Hibernate/POI/Excel/Jackson
workload-app/      Spring Boot 3.4.4 + MyBatis-Plus 3.5.5 + Flyway 10.20.1
                   ⚠ 目前只有 db/migration 与两个一致性测试，无生产 Java 代码
```

| 层         | 内容                          | 谁能改        |
| --------- | --------------------------- | ---------- |
| **L1 参数** | 系数、分档阈值、单价表、额定标准、金额阶梯（89 条） | 教务处，按学期版本化 |
| **L2 派生** | `derive/` 八个纯函数             | 代码         |
| **L3 公式** | `segment/` 六个环节计算器 G1~G6    | 代码         |

**引擎是一个纯函数**：

```java
WorkloadEngine.calc(teacher, term, courses, declarations, recognitions, bonusItems, rules)
    → WorkloadSnapshot
```

聚合根 = **教师 × 学期；九步：解析规则（含输入定序）→ 额定双线 → C1 分组与实习轮次 → 六环节逐行 → 纵向汇总 → 管理服务 → 门槛封顶 → 单价与酬金 → 合规扫描 → 组装快照。**

**L1 参数的唯一权威副本在测试夹具里**：`DefaultRules.java`（89 条）与 `V8__seed_rule_v2026_01.sql` 必须双向同步，`RuleConsistencyTest` 双向比对，防「单元测试全绿而生产算错钱」。

### 2.4 数据模型（V1~V8，24 表 / 31 外键 / 58 CHECK / 6 触发器）

| 迁移 | 内容                                                                                                             |
| -- | -------------------------------------------------------------------------------------------------------------- |
| V1 | 维度与字典：`term` `college` `major`                                                                                 |
| V2 | 规则参数：`rule_version` `rule_scalar` `rule_range` `rule_lookup`                                                   |
| V3 | 教师：`teacher`（身份证三列 AES-GCM/mask/HMAC）`teacher_term_profile`                                                    |
| V4 | 导入与开课：`import_batch` `course_row`                                                                              |
| V5 | 申报与酬金：`declaration` `declaration_attachment` `course_quality_recognition` `course_quality_member` `bonus_item` |
| V6 | 快照：`workload_snapshot` `workload_snapshot_line`（宽稀疏）`workload_snapshot_bonus` `snapshot_issue`                 |
| V7 | 用户审计任务：`audit_log` `sys_user` `calc_job`                                                                       |
| V8 | 规则种子 v2026.01（89 条）                                                                                            |

**关键设计**：快照是唯一读源；`line` 是宽稀疏表（一行 = 一个课程任务，一门课可同时有理论与实践学时，不按环节拆表）；`factor_source_json` 驱动前端 `FactorChip` 四色（蓝=导入/灰=系统/黄=我申报/红=待核）。

### 2.5 功能范围

**一期做**：排课+名册导入、教师申报+教务处代填、G1~G6+汇总、管理服务按区间折算、额定 180/免征/200%封顶/超额酬金、表二其他酬金 7 类、合规告警+数据质量、教师 4 屏+教务处 4 屏、POI 填原模板导出附件1/2。

**一期不做**：三级签字/审批流/院部公示（用户明确本模块不涉及签字）、外聘教师课时酬金、第二课堂计算逻辑（待团委文件）、学期环比、「同一时间只能辅导一门课」校验、院级教务助理角色。

### 2.6 31 项规则裁量（B 的核心资产）

办法未定义/自相矛盾处 28 项 + 实施时新增 3 项（#29~#31），全部已给默认值并记录理由。**其中 5 项标 ⚠ 影响金额量级**：#5 实习 T×8、#7 200% 口径、#21 最低教学取 min、#27 产假降哪条线、#28 实习轮次学期内。

### 2.7 质量保障（B 最强的地方）

- domain 293 测试 + app 9 测试；行覆盖 **99.5%**、分支 **98.7%**；`jacoco:check` 门禁（行≥90/分支≥85）
- jqwik 属性测试**六条不变量**：任意排列≤最优、系数多重集恒等、`excessPayable ≤ excessRaw` 且 ≤180、幂等、单调、**跨 JVM 可重现**（深指纹固定成常量）
- **对账测试是一等交付物**：与真实历史表一/表二**逐格 diff**（13 个教师级字段 + 19 个因子列），验收门是「每格差异都有归类和结论」而非零差异
- 三类错误三种处置：可降级→兜底+DQ issue；违反约束→截断+COMPLIANCE；契约破坏→抛异常
- 15 个告警码（W01~~W10 + DQ01~~DQ05），`SnapshotIssue` 构造器**拒收未登记的码**

## 4. 差异部分（逐模块标注）

## 6. 融合建议与可选方式

> 以下**全部是选项**，未做选择。请按第 7 节逐项确认。  
> 每一处差异给出 2~3 个可选融合方式 + 适用场景 + 取舍。


### 6.0 先决问题：融合的"总方向"

这一项决定其余所有差异的取舍基准，**必须先定**。

#### 方向 ① 「A 宿主 + B 换心」：保留 A 的 Web/审批/导出，用 B 的 domain 引擎替换 A 的 calc 层

- **具体做法**：把 `workload-domain` 作为新 Maven 模块引入 `rear/`；A 的 `biz_*` 表通过适配层装配成 B 的输入 DTO；`SummaryCalcServiceImpl` 改为调 `WorkloadEngine.calc()`；`biz_workload_summary` 增加规则版本与因子快照列。
- **适用场景**：A 已上线/将要上线，前端、审批流、导出、菜单权限都要保留；目标是**把算钱做对**而非重做产品。
- **取舍**：✅ 保留全部已投入的 Web 资产；✅ 立刻获得 B 的测试与对账能力；❌ 两套数据模型要写适配层（B 的 `course_row`/`declaration` ↔ A 的 `biz_teaching_task`/`biz_wl_*`），工作量不小；❌ A 的"系数落明细列"与 B 的"每次推导"会并存一段时间，**同一数字两个来源**，必须明确谁是权威。
- **前置**：必须先定 D2-1（封顶口径），否则换心前后金额突变。

#### 方向 ② 「B 宿主 + A 补外围」：以 B 为基线，把 A 的前端/审批/导出移植过来

- **具体做法**：按 B 的 Plan 2→3→4 推进；A 的 19 个页面与审批状态机作为 Plan 2/3 的输入参考，导出按 A 已实现的列集（19/17 列）补齐。
- **适用场景**：认可 B 的"可重现"红线为第一优先级，愿意接受重做外围、换取长期正确性；审批流可接受从 A 的形态改写或砍掉。
- **取舍**：✅ 架构最干净、测试最完备、"往届可重现"能真正兑现；✅ 不必写适配层（B 是完整数据模型）；❌ **代价最大**，A 的 Web 层基本要重写；❌ 与 B 已定的 D9「不做审批流」冲突，若坚持要审批需重新设计；❌ Plan 2~4 工作量大，且**对账尚缺真实数据**，是最大不确定性。

#### 方向 ③ 「不融合代码，只统一口径」：两项目各自保留，只对齐规则值与裁量默认

- **具体做法**：以 B 的 31 项裁量决策表为基准，逐项与 A 比对；把 A 的规则值改到与 B 一致（或反之）；产出统一的《口径基准表》供两者共同遵守。
- **适用场景**：时间紧、要先把**能发对钱**这件事解决；或两个项目分属不同团队/阶段，短期不合并。
- **取舍**：✅ 成本最低、见效最快、风险最小；✅ 不触碰任何代码架构；❌ 治标不治本——**A 的架构缺陷（系数落明细、规则无版本、无对账）依然存在**；❌ 两套代码长期并存，维护双份。

#### 方向 ④ 「分期：A 交付一期，B 承接二期」

- **具体做法**：A 按现状（补齐 23 个未提交文件 + 修 4 项待办口径）作为一期交付；B 的 Plan 2~4 作为二期重构，届时用真实运行数据做对账。
- **适用场景**：有明确的交付时间点；愿意承担"一期口径错、二期纠"的代价。
- **取舍**：✅ 风险最低、节奏最稳；✅ 二期有真实数据可对账（正是 B 目前最缺的）；❌ 若一期封顶口径（D2-1）取错，**一期就会发错钱**，二期还要追补；❌ 两套系统并行期长。

#### 方向 ⑤ 「只搬文档与决策」：把 B 的决策资产并入 A，不动代码

- **具体做法**：把 B 的 `规则确认单` + 31 项裁量表 + 告警码表 + 对账方法论文档搬入 A 的 `docs/`，用它们校正 A 的口径与认知；A 的代码仍走自己的路线。
- **适用场景**：当前只想**先把口径这件事想清楚**，代码层面暂无计划。
- **取舍**：✅ 成本极低、立即提升 A 的口径严谨度；❌ 完全是文档层面，不解决任何实际计算分歧。

### 6.8 D1 架构与 D4 数据模型

这两项**不建议逐点融合**，它们是"选宿主"的结果：若走 6.0 方向 ①，则以 A 的表为主 + B 的引擎；若走方向 ②，则以 B 的表为主。**逐点融合会产生两套并行的数据模型**，是最高风险的做法。

**若必须并存**（方向 ①/③ 的过渡期），至少要做到：

- 明确**单一权威源**：数字以谁为准必须写进文档
- 规则参数**单向同步**（改一处自动同步另一处，或直接共用一张表）
- 加一条一致性测试：同一输入喂两个引擎，断言输出一致（B 已有 `RuleConsistencyTest` 的成熟范式可借）

### 6.9 D5 审批流：A 有、B 明确不做

| 方式                | 做法                            | 适用场景       | 取舍                                                   |
| ----------------- | ----------------------------- | ---------- | ---------------------------------------------------- |
| ①保留 A 的审批流        | 融合后保留 0→1→2→3 + -1            | 学校确实要三级签字  | ✅ 符合 A 的现行管理需求；❌ 与 B 的 D9 冲突，需重写 B 的快照状态机            |
| ②采纳 B 的无审批 + 三档核验 | 砍掉审批，改为 AUTO/DOC/ATTEST + 线下签 | 认可"签字线下完成" | ✅ 与 B 的设计一致、教务工作量小；❌ **推翻 A 已验证的流程**，且需确认学校是否接受线上无签字 |
| ③并存：审批流 + 三档核验都保留 | 核验管"数据对不对"，审批管"流程走没走完"        | 两者职责被认为都需要 | ✅ 最完整；❌ 复杂度最高，两套状态机要协调                               |
